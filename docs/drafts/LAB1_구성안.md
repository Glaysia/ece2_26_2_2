## 3. 범위와 압축 원칙

레거시의 HDL 입문·모델링·조합논리 약 3주 분량을 기능 중심으로 재구성한다. 모든 회로 변형을 반복 구현하는 대신 대표 회로를 빠르게 만들고 통합한다.

| 반드시 다룰 내용 | 처리 방식 |
|---|---|
| module, 입출력, 내부 신호, 인스턴스 | 작은 실행 예제에서 바로 설명 |
| wire/reg, 비트 폭, 이진·십진·16진 상수 | 실제 코드와 파형 표시에 연결 |

| assign, always @*, if/case | 조합회로의 출력이 모든 경우에 정해지도록 작성 |
| 가산·감산·비교·선택·부호화·복호화 | 기본 실습 6개에서 대표 예제 구현 |

줄이거나 제외할 내용:

- TTL 부품 종류 암기, FPGA 역사, 구형 ISE·Schematic 실습
- 게이트마다 프로젝트를 새로 만드는 절차
- 같은 회로를 세 가지 모델링 방식으로 모두 제출하는 과제
- 카르노맵 풀이의 반복, 게이트 피드백으로 DFF 만들기
- 클록 분주·레지스터·카운터·FSM·동적 FND 스캔 구현: LAB2 이후로 이관

`reg` 선언만으로 플립플롭이 생기는 것은 아니다. 조합 블록은 기본값과 모든 분기를 지정하여 의도하지 않은 래치를 방지한다. 회로 기술의 `for`를 클록에 따른 반복으로 설명하지 않는다.

### 4.1 VS Code 준비와 저장소 받기

1. Git과 VS Code를 설치한다. 설치 후 터미널을 새로 열고 `git --version`으로 Git 실행을 확인한다.
2. 작업할 상위 폴더에서 아래 명령으로 수업 저장소를 받는다. 도구의 경로 문제를 줄이기 위해 작업 경로는 짧은 영문 경로를 권장한다.

```powershell
git clone --branch OT https://github.com/Glaysia/ece2_26_2_2.git
cd ece2_26_2_2
code ece2_26_2_2.code-workspace
```

- 위 명령은 원격에 `OT` 브랜치 또는 태그가 배포되어 있다는 전제다. 현재 로컬 참조에서는 `OT`를 확인하지 못했으므로 배포 전에 확인한다. 태그를 받으면 detached HEAD 상태가 될 수 있으며, 학생 작업은 별도 작업 브랜치에서 진행한다.
- 주소 뒤에 `.git@OT`를 붙이는 것이 아니라 `--branch OT`로 지정한다. 이미 저장소가 있으면 다시 clone하지 않고 현재 변경사항과 배포 기준을 먼저 확인한다.
- `code` 명령이 없으면 VS Code의 **파일 → 파일에서 작업 영역 열기**로 `ece2_26_2_2.code-workspace`를 연다.
- 권장 확장 중 HDL용 `Hudson-River-Trading.vscode-slang`, 파형용 `lramseyer.vaporview`를 설치한다. 확장 설치만으로 시뮬레이션 실행 도구까지 준비되는 것은 아니다.
- 열린 작업 영역에서 HDL 프로젝트 폴더와 소스 위치를 확인한다. 다른 주차의 예제를 LAB1 예제로 착각하지 않는다. LAB1 소스의 최종 배포 경로는 예제 작성 후 이 문서에 반영한다.

레거시의 `Vivado 2022_2 installation.pptx`를 설치 흐름의 참고로 사용한다. 거기에 적힌 2022.2를 이번 수업의 필수 버전으로 그대로 옮기지 않는다. 수업용 버전·설치 화면은 배포 전에 실제 PC에서 통일하여 확인한다.

1. AMD 공식 배포처에서 수업에서 지정한 버전의 설치 프로그램을 받는다.
2. 설치할 제품으로 Vivado를 선택한다. 이번 HDL 실습에 필요하지 않은 도구 전체를 무조건 설치하지 않는다.
3. 대상 FPGA 계열 지원을 포함한다. 신 장비 레거시는 **Spartan-7, `xc7s75fgga484-1`**을 사용한다. 실제 실험실 장비와 같은지 확인한 뒤 최종 지정한다.
4. 설치 구성에서 케이블 드라이버 항목을 확인한다. 설치·드라이버 작업에서 요구하는 권한과 평소 편집기 실행 권한을 구분한다.

### 4.3 소스 파일을 읽는 순서

처음부터 문법을 모두 외우지 않고 **입출력 → 출력 식 → 연결 → 테스트** 순서로 읽는다.

| 구분 | 하는 일 | 학생이 설명할 내용 |
|---|---|---|
| 설계 소스 `.v` | FPGA에 구현할 회로 기술 | 입력·출력의 폭, 출력이 정해지는 조건 |
| 테스트벤치 `.v` 또는 `.sv` | 입력을 넣고 결과를 검사 | 입력 순서, 시간 간격, 예상값, 종료 조건 |
| top 모듈 | 하위 모듈과 외부 포트 연결 | 어떤 출력이 다음 모듈의 어떤 입력으로 가는가 |
| 제약 파일 `.xdc` | 외부 포트와 보드 핀·전기 규격 연결 | 포트 이름, 핀 번호, I/O 규격 |
| 파형 파일 `.vcd` 등 | 시뮬레이션 결과 기록 | 어떤 소스 버전과 테스트에서 생성했는가 |
| 프로젝트 `.xpr` | Vivado의 소스·설정 관리 | 실제 등록된 파일과 선택된 top |

첫 예제는 아래 정도의 AND 회로로 시작한다. 다음 코드는 문서 내 설명 예제이며, 아직 별도 소스 파일이 배포되었다는 뜻은 아니다.

```verilog
module and_gate (
    input  wire a,
    input  wire b,
    output wire y
);
    assign y = a & b;
endmodule
```

- `module`부터 `endmodule`까지가 회로 하나다. `a`, `b`는 입력, `y`는 출력이다.
- `assign`은 “한 번 계산하고 끝”이 아니라 입력에 따른 출력의 관계를 계속 유지한다.
- `a & b`는 두 입력이 모두 1일 때만 1이다. 이 회로에는 클록이 필요 없다.

```verilog
`timescale 1ns/1ps
module tb_and_gate;
    reg a, b;
    wire y;

    and_gate dut (.a(a), .b(b), .y(y));

    initial begin
        $dumpfile("tb_and_gate.vcd");
        $dumpvars(0, tb_and_gate);
        a = 0; b = 0;
        #10; a = 0; b = 1;
        #10; a = 1; b = 0;
        #10; a = 1; b = 1;
        #10;
        $finish;
    end
endmodule
```

- 테스트벤치가 회로 입력을 직접 바꾸므로 `a`, `b`를 `reg`로 선언한다. 이것이 FPGA의 레지스터를 만들라는 뜻은 아니다.
- `.a(a)`의 왼쪽 `a`는 설계 모듈의 포트, 괄호 안 `a`는 테스트벤치의 신호다. `dut`는 검사 대상 회로의 인스턴스 이름이다.
- 시간 단위가 1ns이므로 `#10`은 10ns 대기다. 총 40ns를 실행한다. 이 대기는 테스트 입력 간격이지 실제 AND 게이트의 지연시간이 아니다.
- `$dumpfile`, `$dumpvars`는 VCD 출력용이다. 사용하는 시뮬레이터의 지원·파형 저장 방식에 맞춰 실행 설정을 검증한다. Vivado 내장 파형은 별도로 확인한다.
- `$finish`는 시뮬레이션을 끝낸다. 테스트벤치의 시간 지연·덤프·종료 코드를 FPGA 설계 소스에 넣지 않는다.

### 4.4 VS Code 시뮬레이션과 VaporView — 자세히

### 4.5 Vivado 프로젝트 구성과 시뮬레이션 — 간단히

프로젝트 생성 절차는 레거시 신 장비 Lab-02를 기반으로 하되, 같은 파일을 VS Code와 Vivado에서 공유한다. 파일 복사본을 따로 수정해 결과가 달라지는 상황을 피한다.

1. **Create Project → RTL Project**에서 프로젝트 이름·저장 위치를 지정한다.
2. 실험실 장비의 정확한 부품을 선택한다. 레거시 기준은 `xc7s75fgga484-1`이며 보드 확인 후 확정한다.
3. **Add or create design sources**에 설계 모듈을 등록한다. 하위 모듈도 빠짐없이 포함하고, 저장소의 원본 파일을 참조하도록 복사 옵션·실제 파일 경로를 확인한다.
4. **Add or create simulation sources**에 테스트벤치를 등록한다. `.sv` 파일은 SystemVerilog로 인식되는지 확인한다.
5. Design Sources에서는 실제 보드용 모듈을 **Set as Top**, Simulation Sources에서는 해당 테스트벤치를 **Set as Top**으로 지정한다. 두 top은 역할이 다르다.
6. **Run Simulation → Run Behavioral Simulation**을 실행한다. AND 예제라면 40ns 종료까지 실행하고 네 입력의 결과를 확인한다.
7. 필요한 신호를 추가하고 전체 구간을 표시한다. VS Code에서 확인한 동일 입력의 값과 비교한다.

- `.xpr`이 열린다는 것만으로 소스가 등록된 것은 아니다. Sources 계층에 의도한 모듈이 보이는지 확인한다.
- 파형이 없으면 테스트벤치 top, 실행 시간, 신호 추가 여부를 먼저 본다. 컴파일 오류는 로그의 첫 오류부터 해결한다.
- 실험 후 보고서에는 대표 파형과 일치 여부를 짧게 정리한다. 실험 전 보고서의 모든 파형 설명을 반복하지 않는다.

> 스크린샷 자리 S06: Design Sources와 Simulation Sources의 서로 다른 top 및 하위 모듈 계층.
>
> 스크린샷 자리 S07: Vivado의 대표 시뮬레이션 파형 한 장. VS Code와 동일한 테스트 조건을 캡션에 적는다.

### 4.6 합성 → 구현 → 비트스트림 → JTAG

| 단계 | 의미 | 다음 단계로 가기 전 확인 |
|---|---|---|
| Simulation | 입력을 넣어 HDL 동작 검사 | 예상값과 실제값 일치 |
| Synthesis | HDL을 FPGA 논리 자원으로 변환 | top·포트 정상, 의도하지 않은 래치·다중 구동 없음 |
| Implementation | 논리 자원을 칩에 배치하고 배선 | 핀·전기 규격·제약 및 구현 오류 확인 |
| Generate Bitstream | FPGA 구성 데이터 생성 | 성공 로그와 생성된 `.bit` 경로 |
| JTAG | 실제 FPGA에 구성 데이터 전달 | 대상 장치·파일 확인 후 실제 입출력 검사 |

1. **Add or create constraints**에 보드용 XDC를 등록한다. top의 각 외부 포트와 `get_ports` 이름·비트 인덱스가 같아야 한다.
2. 핀 번호는 실제 보드의 검증된 핀맵을 사용한다. `IOSTANDARD`도 보드 전압에 맞춘다. 레거시 핀·극성을 확인 없이 복사하지 않는다.
3. **Run Synthesis**를 실행한다. 실패하면 첫 오류를 확인한다. 조합회로 실습에서 의도하지 않은 래치가 생기면 출력 기본값과 빠진 분기를 확인한다.
4. **Run Implementation**을 실행하고 오류·주요 경고·제약 보고서를 확인한다. 조합회로라는 이유로 제약 경고를 모두 무시하지 않는다. 클록이 없는 회로에 가짜 클록을 추가하지 않는다.
5. **Generate Bitstream**을 실행한다. 성공한 설계 버전과 `.bit` 파일을 연결해서 기록한다. 파형 확인용 VCD와 FPGA에 넣는 비트스트림은 다른 파일이다.
6. 보드 전원·USB/JTAG 연결 후 **Open Hardware Manager → Open Target → Auto Connect**로 장치 인식을 확인한다.
7. 대상 FPGA의 **Program Device**에서 방금 생성한 `.bit`를 선택한다. 완료 후 대표 입력을 조작해 LED·FND 출력을 확인한다.

**JTAG 절차는 2026년 9월 7일 실험실에서 직접 검증할 예정이다.** 위 6~7번은 레거시에 따른 진행안이며, 케이블 종류·드라이버·보드 설정·메뉴·실제 동작을 확인한 후 확정한다. 현재 장비 검증 완료로 표기하지 않는다.

- JTAG 다운로드와 비휘발성 메모리 기록은 구분한다. 이번 절차는 FPGA 구성 다운로드 기준이며 전원을 껐다 켠 뒤 유지되는 설정까지 다룬 것으로 간주하지 않는다.
- 보드에서만 틀리면 먼저 XDC·입출력 극성·선택된 top·다운로드한 파일을 확인한다. HDL을 무작정 바꾸지 않는다.

> 스크린샷 자리 S08: 합성·구현·비트스트림 완료 상태와 확인할 메시지.
>
> 스크린샷 자리 S09: 9월 7일 검증 후 JTAG 장치 인식·Program Device 화면 및 보드 입출력 사진. 학생이 꽂을 커넥터와 전원 상태를 식별할 수 있게 촬영한다.

## 5. 기본 실습 6개

### 실습 1 — 게이트와 비트 연산

- 제공된 AND 예제를 실행한 뒤 OR·XOR·NOT으로 확장한다.
- 1비트 진리표에서 4비트 벡터 연산으로 확장한다.
- `&`와 `&&`, `~`와 `!`의 차이를 실제 결과로 확인한다.
- 검증: 2입력 게이트의 네 경우를 모두 확인하고, 벡터 입력 `0011`, `0101`의 결과를 예상·비교한다.

### 실습 2 — 반가산기와 전가산기

- 반가산기의 합·자리올림을 구현한다.
- 반가산기 두 개와 OR 연산을 연결하여 전가산기를 구성한다.
- 포트는 이름으로 연결하고 외부 포트와 내부 연결 신호를 구분한다.
- 검증: 반가산기 4가지, 전가산기 8가지 입력을 모두 검사한다.

### 실습 3 — 4비트 가산기·감산기

- `a[3:0]`, `b[3:0]`의 덧셈과 뺄셈을 구현한다.
- 덧셈은 입력을 5비트로 확장하여 carry를 보존한다.
- 뺄셈 결과는 하위 4비트로 표현하고 borrow는 `a < b`로 별도 표시한다.
- 검증: `0+0`, `15+1`, `15+15`, `0-1`, `15-15`, `3-5`를 포함한다.
- 기본 입력은 unsigned다. 음수의 signed 해석은 비교 설명으로 구분한다.

### 실습 4 — 비교기와 MUX

- 두 4비트 입력의 `a>b`, `a==b`, `a<b`를 구현한다.
- 선택 신호로 여러 결과 중 하나를 출력하는 MUX를 만든다.
- 조합 `always @*`, blocking 할당(`=`), `if/case`와 기본값을 다룬다.
- 검증: 대소·동일 조건, 모든 선택값, 입력과 선택 신호 변경을 확인한다.

### 실습 5 — 인코더·디코더·7세그먼트

- 4입력 우선순위 인코더를 만든다. 높은 비트 우선, 무입력은 `valid=0`, 코드 0으로 정한다.
- 2비트 코드를 4비트 one-hot 출력으로 바꾸는 디코더를 만든다.
- 4비트 값을 한 자리 16진수 `0~F`의 세그먼트 패턴으로 변환한다.
- 검증: 인코더 16가지 입력, 디코더 4가지 입력, 표시값 16가지를 확인한다.
- 세그먼트 순서·극성은 배포 보드에 맞게 명시한다. 여러 자리의 동적 스캔은 구현하지 않는다.

### 실습 6 — 모듈 연결과 표시

- 연산기, 선택 회로, 표시 디코더를 top에서 연결한다.
- 모듈별 테스트와 연결 후 테스트를 구분한다.
- 검증: 포트 순서·폭·누락, 출력 극성, top 및 XDC 포트 이름을 확인한다.
- 실습 1~5를 매번 별도 프로젝트로 만들지 않고 모듈을 재사용한다.

### 각 소스코드에서 짚을 내용

아래 이름은 제작할 예제의 모듈명 제안이다. 실제 파일을 작성하면서 이름·포트·테스트벤치를 이 표와 일치시킨다. 각 예제 설명은 **입출력 표 → 핵심 코드 → 예상값 → 파형 해석** 순서로 통일한다.

| 모듈명 제안 | 핵심 코드·설명 | 확인할 대표 결과 |
|---|---|---|
| `logic_gates` | `a & b`, `a \| b`, `a ^ b`, `~a`; 각 비트가 독립적으로 계산됨 | a=0011, b=0101이면 AND=0001, OR=0111, XOR=0110 |
| `half_adder` | `sum = a ^ b`, `carry = a & b`의 진리표 | 1+1이면 sum=0, carry=1 |
| `full_adder` | 반가산기 두 개의 중간 합·carry 연결, 두 carry의 OR | a=b=cin=1이면 sum=1, cout=1 |
| `add_sub4` | `{1'b0, a} + {1'b0, b}`로 폭 확장; 결과 하위 4비트와 carry 분리 | 15+1 → result=0, carry=1; 3−5 → result=14, borrow=1 |
| `comparator4` | `>`, `==`, `<`; unsigned 입력 범위 | a=15, b=1이면 gt=1; signed 비교와 혼동하지 않음 |
| `mux4` | 4비트 데이터 네 개 중 하나를 2비트 선택값으로 출력; `always @*`와 `case` | 선택되지 않은 입력만 바꾸면 출력은 그대로 |
| `priority_encoder4` | 높은 비트부터 `if/else if`; 무입력과 입력 0번을 `valid`로 구분 | 1010 → code=3, valid=1; 0000 → code=0, valid=0 |
| `decoder2to4` | 입력 네 경우를 `case`로 one-hot에 대응 | 00 → 0001, 11 → 1000 |
| `hex7seg` | 0~F를 켤 세그먼트 집합에 대응; 보드 극성과 논리 패턴 구분 | 0은 a~f, 1은 b·c; b·d는 소문자 형태로 표시 가능 |
| `lab1_top` | 연산·선택·표시 연결 및 보드 포트 대응; 회로를 복사하지 않고 인스턴스화 | 같은 result에 대해 연산 출력과 표시 디코더 입력이 일치 |
| 각 `tb_*` | 입력 생성·예상값 비교·실패 메시지·종료; 설계 모듈을 검사 대상으로 연결 | 정상 입력뿐 아니라 경계·우선순위·무입력까지 검사 |

- 벡터 `a=0011`, `b=0101`에서 `a && b`는 1비트 1이다. `~a`는 1100, `!a`는 1비트 0이다. 연산자 모양만 비슷하다고 바꾸지 않는다.
- 비트별 NAND는 `~(a & b)`로 쓴다. 레거시의 `a ~& b` 표기는 그대로 사용하지 않는다. `~&a`는 여러 비트를 하나로 줄이는 reduction NAND로 다른 연산이다.
- 비교기에서 이미 알고 있는 0/1 입력이라면 gt·eq·lt 중 정확히 하나가 1이어야 한다.
- 우선순위 인코더 뒤에 디코더를 연결해도 다중 입력이 원상 복구되지는 않는다. `1010`은 선택된 최상위 비트 `1000`으로 복호화되며, 무입력은 `valid`를 함께 해석해야 한다.
- 7세그먼트는 코드보다 먼저 a~g 위치 그림과 켜질 segment 표를 보여준다. 비트 순서·점(dp)·자리 선택 신호는 보드 검증 후 확정하고, 순차회로가 필요한 여러 자리 스캔은 넣지 않는다.

> 스크린샷 자리 S10: 실습별 대표 파형. 가산기의 carry, MUX의 선택 변화, 인코더의 다중 입력·무입력, 디코더의 one-hot을 설명할 수 있는 구간을 고른다. 모든 GUI 클릭 화면을 반복해서 넣지 않는다.

## 6. 사전 공개 통합 실습 — 4비트 미니 연산기

이 실습은 사전에 공개하는 기본 결과물이다. 14시에 공개하는 응용과제와 구분한다.

### 입출력과 동작

| 신호 | 폭 | 의미 |
|---|---:|---|
| a, b | 각 4비트 | unsigned 입력 0~15 |
| op | 2비트 | 연산 선택 |
| result | 4비트 | 연산 결과의 하위 4비트 |
| carry | 1비트 | 덧셈의 자리올림, 다른 연산에서는 0 |
| borrow | 1비트 | 뺄셈에서 a<b이면 1, 다른 연산에서는 0 |
| seg | 보드에 맞게 정의 | result의 한 자리 16진수 표시 |

| op | 연산 | 확인할 사항 |
|---|---|---|
| 00 | a+b | 하위 결과와 carry 분리 |
| 01 | a-b | 모듈로 16 결과와 borrow 분리 |
| 10 | a AND b | 비트 단위 연산 |
| 11 | a XOR b | 비트 단위 연산 |

보드에서는 스위치로 입력·연산을 선택하고, 결과는 한 자리 FND, carry·borrow는 LED로 표시한다. 실제 스위치 수와 FND의 정적 자리 선택 가능 여부를 확인한 뒤 핀을 확정한다. 인터페이스 제약이 있으면 입력 배치 또는 표시 방법을 수정하고 이 명세에도 반영한다.

### 검증 기준

- `op`, `a`, `b`의 조합 4×16×16=1024개를 자동 검사한다.
- 기준값은 요구사항에서 계산한다. DUT 내부 신호를 정답으로 사용하지 않는다.
- 파형에는 대표 정상 입력과 carry·borrow 발생 입력을 표시한다.
- 보드에서는 연산별 대표 입력과 경계 입력을 확인한다. 1024가지를 수동 조작하지 않는다.
- 값이 맞지 않으면 논리 오류, 테스트벤치 오류, 포트 연결, 핀·극성을 구분하여 기록한다.

- 발표·교안·공개 예제에 당일 변경 조건이나 정답을 미리 포함하지 않는다.
- 사전 보고서는 공개 기본 실습을 대상으로 하며, 미공개 응용과제의 사전 구현을 요구하지 않는다.
