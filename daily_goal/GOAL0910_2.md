현재 템플릿의 첫 회로는 [프로젝트 설정](../example/fpga_projects_hdl/LAB1/vivado_2026_1/01_logic_gates/project.json)에서 `../../common/rtl/logic_gate.v`, 공통 TB, 공통 XDC를 참조한다. 이 상태에서는 학생이 회로를 작성하지 않고 task만 실행해도 제작자의 결과를 재현할 수 있다. 소스 화면을 많이 넣고 버튼을 자세히 설명했더라도, 학생이 입력·수정·실패·해결하는 과정이 빠지면 수업 목표를 충족하지 못한다.

| 현재 시작 방식 | 개편할 학습 행동 | 학생이 설명할 내용 |
|---|---|---|

| 만들어진 XPR 열기 | New Project에서 자신의 파일을 직접 등록 | RTL·TB·XDC의 파일셋과 top 구분 |

## 2. 학생용 템플릿은 작은 시작 틀로 만든다

**템플릿 저장소 하나에는 프로젝트 하나와 workspace 하나만 둔다.** `fpga-lab-template`은 모든 22개 실습이 똑같이 clone하는 범용 시작 틀이다. 회로별 템플릿 저장소나 22개 하위 프로젝트를 만들지 않는다. 완성 예시 22개는 각각 독립 저장소로 구성하여 `C:/Users/UOS/Documents/ece2_26_2_2` 강의 저장소의 서브모듈로 연결한다.

모든 회로에 공통으로 쓰는 학생용 시작 구조는 다음을 기준으로 한다. 아래는 개편 예정 구조다. 각 PDF에서 실습에 맞는 파일명으로 바꾸고 직접 작성한다.

```text
fpga-lab-template/
  README.md
  LAB1.code-workspace
  .gitignore
  src/
    design.v                  # 작성 위치를 알리는 주석만
  sim/
    tb_design.v               # 작성 위치를 알리는 주석만
  constraints/
    pins.xdc                  # 핀 표를 보고 작성하라는 주석만
  tools/                     # 도구 검사·시뮬레이션·파형 열기 보조
```

- 세 실습 파일은 학생이 Explorer에서 바로 열 수 있도록 파일명과 역할 안내만 넣는다. 동작하는 완성 모듈·입력 자극·핀 배정은 넣지 않는다. 학생이 PDF를 보고 입력할 본문을 남긴다.
- `README.md`는 같은 clone 명령, workspace 열기, 선택한 실습 PDF의 파일 작성 단계만 우선 안내한다. 파일명 변경은 Explorer의 Rename 동작으로 보여 준다.
- `COMMON`, 다른 회로 9개의 정답, 통합 모듈 전체, 정답 TB, 완성 XDC, XPR, bit, 제작자의 PASS 로그는 기본 템플릿에서 제외한다.
- 기존 완성본은 독립 예시 저장소로 이관하고 강의 저장소에서 서브모듈로 연결한다. 원본·참고·제작 검증 자료를 보존한다. 공개 템플릿의 현재 커밋 `11573c4`와 강의 저장소 `3a52198`을 이전 배포 기준으로 기록하고 기존 Git 이력을 지우지 않는다.
- 학생용 task는 **01 Check tools / 02 Simulate / 03 Open waveform** 세 개를 유지한다. 도구 검사만 초기 상태에서 성공할 수 있으며, 미작성 회로의 시뮬레이션을 성공으로 표시하지 않는다.
- 실행기는 현재 workspace의 `src`와 `sim` 파일만 사용한다. 완성 코드 복사·다운로드·대체, 다른 프로젝트나 교사용 공통 RTL로의 자동 전환을 하지 않는다.
- 실행 명령과 사용한 RTL·TB 경로를 보여준다. 학생이 파일을 수정하면 바로 그 파일이 다시 컴파일되어야 한다. 실행 보조 스크립트의 구조를 이해해야만 회로 실습을 시작할 수 있게 만들지 않는다.
- 파일 이름이나 모듈 이름을 바꾸는 후속 실습은 새 이름과 task의 변경 위치를 해당 PDF에 명시한다. 소스 목록을 자동으로 추측해 다른 회로까지 컴파일하지 않는다.
- task 04·05·06과 자동 Vivado 프로젝트 생성·합성·구현은 학생 workspace에 넣지 않는다. Vivado 단계는 GUI로 직접 진행한다.
- 다른 회로를 시작할 때도 같은 URL을 새 목적지 이름으로 clone한다. 한 clone 안에서 22개 프로젝트를 선택하는 방식으로 되돌리지 않는다. CLI 선택 시 도구 검사·시뮬레이션은 Icarus 등 오픈소스만 사용하고 Vivado 설치나 XSim을 요구하지 않는다.

**저장소 소스를 찾아 복사할 줄 아는 학생은 복사해도 된다는 기존 방침은 유지한다.** 복사 방지나 정답 은닉을 위한 접근 제한을 만들지 않는다. 기본 수업 동선을 직접 작성 중심으로 만들고, 학습 여부는 코드 설명·변경 과제·파형 해석으로 확인한다.

### 2.1 학생은 매 실습을 같은 명령으로 시작한다

```sh
git clone https://github.com/Glaysia/fpga-lab-template.git new_project_name
cd new_project_name
code LAB1.code-workspace
```

예를 들어 다음 두 명령의 URL은 같다. 결과 폴더 이름과 학생이 작성할 내용만 다르다.

```sh
git clone https://github.com/Glaysia/fpga-lab-template.git lab1_01_logic_gates
git clone https://github.com/Glaysia/fpga-lab-template.git lab1_10b_integrated_cli
```

- 최신·레거시·두 통합본 모두 이 방식으로 시작한다. PDF의 첫 명령이 완성 예시 저장소를 clone하거나 예시 서브모듈을 여는 명령이어서는 안 된다.
- 새 목적지에는 하나의 프로젝트와 `LAB1.code-workspace` 하나만 있다. 경로·task는 목적지 이름에 의존하지 않게 한다.
- 학생 제출용 원격은 별도 단계에서 설정한다. clone으로 생긴 템플릿 원격에 제출하지 않도록 기존 `origin`을 `template`으로 이름을 바꾸고 자신의 저장소를 `origin`으로 등록하는 순서를 설명한다.
- GUI로 workspace를 여는 절차도 같은 폴더를 사용한다. clone·code 명령은 PDF에서 복사 가능한 텍스트로 제공한다.

### 2.2 완성 예시 22개는 강의 저장소의 서브모듈이다

| 저장소 | 담을 내용 | 기본 사용 동선 |
|---|---|---|
| `fpga-lab-template` 1개 | 한 프로젝트의 빈 작성 틀·workspace·도구 실행 보조 | 학생이 매번 새 이름으로 clone |
| 완성 예시 저장소 22개 | 저장소마다 완성 실습 1개·workspace 1개·자체 소스·검증 근거 | PDF 참고·완성 결과 대조 |
| `ece2_26_2_2` 강의 저장소 | TeX·PDF·계획·레포트 안내와 예시를 가리키는 gitlink 22개 | 교재와 예시의 통합 탐색 |

예시의 강의 저장소 내 위치는 기존 분류를 유지한다. 아래 각 회로 디렉터리를 독립 저장소의 서브모듈로 전환할 계획이다.

```text
ece2_26_2_2/
  .gitmodules
  example/fpga_projects_hdl/LAB1/
    vivado_2026_1/01_logic_gates/   # 예시 서브모듈 1개
    ...                           # 최신 개별 합계 10개
    vivado_2026_1/11_integrated/   # 예시 서브모듈 1개
    opensource_cli/integrated/     # 예시 서브모듈 1개
    legacy/01_logic_gates/         # 예시 서브모듈 1개
    ...                           # 레거시 개별 합계 10개
```

- 각 예시도 같은 단일 템플릿에서 출발하여 구현한다. 예시 하나만 독립 clone해도 필요한 RTL·TB·XDC·workspace가 모두 들어 있게 한다. 다른 서브모듈이나 상위 `../../common`을 실행 의존성으로 두지 않는다.
- 예시 원격 저장소의 이름·URL·강의 저장소 경로·고정 커밋·사용 템플릿 커밋을 22행 대응표로 관리한다. 아직 만들지 않은 원격을 존재하는 링크처럼 안내하지 않는다.
- 현재 일반 디렉터리를 곧바로 지우지 않는다. 새 예시 저장소의 원본·파일·검증 기록·링크를 대조하고 원격에서 독립 clone이 되는 것을 확인한 뒤 해당 경로를 gitlink로 전환한다.
- `.gitmodules`와 각 예시 커밋을 강의 저장소에 기록한다. 예시 수정은 예시 저장소에 먼저 커밋·push하고 강의 저장소에서는 그 커밋을 가리키도록 갱신한다.
- 교사용 전체 취득은 `git clone --recurse-submodules` 또는 기존 clone의 `git submodule update --init --recursive`로 안내하고 새 폴더에서 확인한다. 학생의 첫 실습은 이 명령을 요구하지 않는다.
- PDF·위키의 예시 링크는 서브모듈 안 파일이 부모 GitHub의 일반 파일인 것처럼 생성하지 않는다. 파일 링크는 실제 예시 저장소의 고정 커밋으로 연결한다. 템플릿 시작 링크와 완성 예시 링크를 명확히 표시한다.

## 3. 첫 회로를 처음부터 다시 구성한다

먼저 [최신 01 논리 게이트 TeX](../weekly-slides/weekly-slides/LAB1_FPGA_0914/04.LAB1_01_LOGIC_GATES_VIVADO.tex)를 기준 예제로 고친다. 한 회로를 학생의 시작 상태에서 끝까지 검증한 뒤 나머지에 확장한다.

### 3.1 템플릿 clone → 파일 열기

1. Git·VS Code·실제 시뮬레이터의 설치와 버전을 확인한다. 필요한 설치 자료로 연결한다.
2. `git clone https://github.com/Glaysia/fpga-lab-template.git lab1_01_logic_gates`로 첫 프로젝트를 만든다. 다른 실습도 같은 URL에 새 목적지 이름을 사용한다. 자신의 제출 원격 설정은 별도 단계로 설명한다.
3. File → New Window → Open Workspace from File... → `LAB1.code-workspace`를 선택한다.
4. Explorer → `src` → `design.v`를 Rename으로 `logic_gate.v`로 바꿔 열고 주석만 있는 파일을 확인한다. 파일 탭·저장 표시·확장자를 설명한다.
5. `sim/tb_design.v`와 `constraints/pins.xdc`도 각각 `tb_logic_gate.v`, `logic_gate.xdc`로 이름을 바꾼다. task가 읽을 RTL·TB 파일명과 top을 지정하는 위치를 화면으로 보여 준다.

### 3.2 RTL을 직접 입력한다

1. 먼저 입력 `a`, `b`와 출력 `x`, `y`, `z`의 의미를 정리하고 네 입력 조합의 진리표를 작성한다.
2. PDF의 실제 VS Code 코드 이미지를 보며 모듈 선언, 포트, AND·OR·XOR 식, 모듈 끝을 차례로 입력한다.
3. 각 코드 묶음 아래에 포트 방향·연산자·연결 관계를 설명한다. 완성 코드 이미지 한 장 뒤에 곧바로 실행 버튼으로 넘어가지 않는다.
4. File → Save All을 누르고 파일 탭의 미저장 표시가 사라졌는지 확인한다.
5. 문법 오류가 나오면 오류 메시지의 파일·줄을 찾아 해당 `.v`를 열어 고치는 예를 한 번 보여준다.

### 3.3 TB도 직접 입력하고 예상값을 대조한다

1. `sim/tb_logic_gate.v`를 열어 시간 단위, 입력 변수, 출력 신호, DUT 인스턴스, 포트 연결을 입력한다.
2. 첫 TB는 `00 → 01 → 10 → 11`을 일정한 간격으로 인가하는 짧은 형태로 설명한다. DUT·입력 자극·파형 덤프·종료의 역할을 각각 읽는다.
3. 예상값은 먼저 쓴 진리표에서 가져온다. RTL의 식을 그대로 복제한 식만으로 정답을 검증하는 습관을 만들지 않는다.
4. 파형을 수동으로 읽는 과정을 마친 뒤 네 입력의 기대값 검사와 실패 메시지를 추가하는 순서로 구성한다. TB 코드도 PDF를 보며 학생이 입력한다.
5. 실행기 종료 코드가 0이라는 것과 회로의 예상 출력이 맞는다는 것을 구분한다. 초기 파형 관찰 단계에 기존 자기검사 PASS 문자열을 강요하지 않고, 자기검사를 추가한 단계에서 검사 수와 결과를 확인한다.

### 3.4 XDC를 직접 입력한다

1. RTL 포트명과 보드 스위치·LED의 대응표를 먼저 작성한다.
2. 현재 검증된 제약의 기준은 `a→K4`, `b→N8`, `x→L4`, `y→M4`, `z→M2`다. PDF에는 [기존 제약](../example/fpga_projects_hdl/LAB1/common/constraints/logic_gate.xdc)과 [원본 대응 자료](../example/fpga_projects_hdl/LAB1/docs/legacy-provenance.md)를 근거로 함께 제시한다.
3. `constraints/logic_gate.xdc`를 열어 `PACKAGE_PIN`, `get_ports`, `IOSTANDARD`를 포트별로 직접 입력한다. LVCMOS33 설정과 핀 번호를 어디에서 확인했는지 설명한다.
4. 대소문자·비트 인덱스·포트명·중복 핀을 확인한다. 잘못된 `get_ports` 대상이나 누락 제약을 찾아 고치는 예를 넣는다.
5. 수정 연습은 확인된 LED 핀 사이의 출력 배정 변경처럼 정해진 범위로 진행한다. 임의의 패키지 핀을 고르게 하지 않는다. 원래 배정과 변경 배정을 표에 기록한다.

**기능 시뮬레이션은 RTL과 TB의 논리 동작을 검사한다. XDC의 실제 핀 배정이 옳다는 것을 증명하지 않는다.** 현재 [실행기](../example/fpga_projects_hdl/LAB1/tools/lab1.py)의 사전 시뮬레이션도 RTL·TB를 입력으로 사용한다. XDC는 VS Code에서 직접 작성·검토하고, Vivado 과정은 포트·핀 화면과 구현 검사에서, CLI 과정은 nextpnr의 제약 처리·배치배선 보고서에서 확인한다. 실제 핀 연결은 보드 실험에서 검증한다. XDC를 바꿨으니 논리 파형도 바뀌어야 한다는 설명을 넣지 않는다.

### 3.5 저장 → 사전 시뮬레이션 → 수정 → 재실행

1. 세 파일을 저장하고 01 Check tools → 02 Simulate를 실행한다. 출력에 자신이 편집한 파일 경로가 나타나는지 확인한다.
2. 03 Open waveform → 파형 뷰어에서 입력·출력을 추가하고 Zoom Fit과 커서로 네 조합을 읽는다.
3. 학생이 진리표에 예상값·실측 시뮬레이션 값을 나란히 채운다. 출력 신호 하나씩 근거를 설명한다.
4. XOR 식을 OR로 바꾸는 수정 실험을 한다. `a=b=1`에서 어떤 출력이 달라질지 먼저 예측하고 저장·재실행한다.
5. 파형과 자기검사가 실제 차이를 보여 주는지 확인한다. TB의 기대값은 원래 XOR 명세를 유지하여 오류를 검출한다. 이후 식을 복구하고 다시 검증한다.
6. 이전 VCD가 그대로 열린 경우 새 결과를 다시 열거나 갱신하는 동작을 설명한다. 실패한 실행에서 이전 PASS·파형을 현재 결과로 보여 주지 않는다.
7. RTL·TB·XDC 작성 과정과 사전 결과를 실험 전 레포트에 남긴다.

### 3.6 자신의 파일을 Vivado로 가져간다

1. Vivado → Create Project → 프로젝트 이름·새 출력 폴더 → RTL Project → 대상 부품 `xc7s75fgga484-1`을 차례로 선택한다.
2. Add Design Sources에는 학생 폴더의 `src/logic_gate.v`를 등록한다.
3. Add Simulation Sources에는 학생 폴더의 `sim/tb_logic_gate.v`를 등록한다. TB를 합성용 RTL에 넣지 않는다.
4. Add Constraints에는 학생이 작성한 `constraints/logic_gate.xdc`를 등록한다.
5. 파일 선택 대화상자에서 경로를 확인하고 Copy sources 옵션을 끈다. VS Code에서 편집하는 파일과 Vivado가 사용하는 파일이 같은지 Sources의 파일 속성으로 확인한다.
6. 설계 top `logic_gate`, 시뮬레이션 top `tb_logic_gate`를 따로 확인한다. 완성 XPR을 열어 이 단계를 건너뛰지 않는다.
7. Run Simulation → Run Behavioral Simulation에서 동일 입력을 확인한다. 사전 시뮬레이션과 파형·예상값을 비교한다.
8. Elaborated Design 등의 포트·I/O 화면에서 HDL 포트와 XDC 핀 대응을 확인한다. 논리 시뮬레이션 PASS와 핀 제약 확인 결과를 따로 기록한다.
9. Run Synthesis → Run Implementation → Generate Bitstream을 GUI에서 직접 실행한다. 실제 완료 화면·경고·출력 파일을 확인한다.
10. 실험실에서 Hardware Manager → 장치 연결 → Program Device를 수행하고, 스위치·LED의 동작과 변경한 핀 배정을 실물로 확인한다. 사진·영상·소스·결과를 자신의 GitHub에 올려 실험 후 레포트에 연결한다.

- 학생이 이미지를 보며 **코드 전체를 입력할 수 있어야 한다.** 잘린 코드, 생략 부호, 너무 작은 글씨로 필수 줄을 숨기지 않는다. 긴 파일은 의미 단위로 나누고 파일명·줄 범위·다음 장의 연결을 적는다.
- 이미지 위 OCR 층이나 선택 가능한 HDL 코드의 중복 본문을 넣지 않는다. clone 명령·경로·파일명은 복사 가능한 텍스트로 제공한다.
- 각 단계에 ‘열 파일 → 입력·수정할 부분 → 저장 → 실행·확인 → 다음 단계 조건’을 넣는다. 완성 소스를 열어 보기만 하는 페이지는 작성 단계로 바꾼다.

- 기존 완성본 화면은 참고 결과로 재사용할 수 있다. 새로 clone한 학생용 틀에서 직접 작성한 검증인 것처럼 표시하지 않는다. 바뀐 폴더·파일명·top·task·등록 경로는 새 실제 화면으로 교체한다.
- 새 PNG는 제작 저장소에서 계속 ignore하고 PDF를 커밋한다. 학생 저장소에서 자신의 레포트용 사진·파형 캡처를 올리는 것은 별도 정책으로 유지한다.

## 6. CLI는 Vivado 없이 bit 생성부터 openFPGALoader까지 완성한다

### 6.1 현재 CLI 교안의 잘못된 종료 경로를 교체한다

사용자가 지적한 다운로드본 `04.LAB1_10B_INTEGRATED_CLI.pdf`는 56쪽이다. 확인한 51쪽은 CLI bit 실패 뒤 Vivado bit 사용을 안내하고, 52–53쪽은 Hardware Manager·Program Device, 56쪽은 Vivado 버전·시뮬레이션을 요구한다. [현재 강의 저장소의 같은 자료](../weekly-slides/weekly-slides/LAB1_FPGA_0914/04.LAB1_10B_INTEGRATED_CLI.pdf)와 [생성기](../weekly-slides/tools/lab1_series.py)의 CLI 사후 단계도 함께 수정한다.

**CLI 실습의 사용자는 Vivado를 사용할 수 없다는 조건으로 전체 경로를 작성한다.** Vivado 설치·XSim·Hardware Manager·Vivado에서 미리 생성한 bit를 필수 단계나 우회 완료 경로로 넣지 않는다. 설치, 학생 소스 작성, 기능 시뮬레이션, 합성, 배치배선, bit 생성, 장치 기록까지 이 조건을 지킨다.

공식 [nextpnr-xilinx 안내](https://github.com/openXC7/nextpnr-xilinx)는 XC7의 Project X-Ray·FASM 흐름을 Vivado 없이 bit를 생성하는 경로로 설명한다. 따라서 이전의 특정 S75 DB 조합 실패를 CLI 전체의 불가능 판정으로 바꾸지 않는다. 이 일반 흐름의 존재와 우리 S75 부품·핀·통합 회로에서 실제로 성공했다는 증거는 구분하여 검증한다.

### 6.2 비트스트림 생성 문제는 해결할 작업으로 남긴다

이전 결과는 APIO openXC7 2026.08.20·해당 X-Ray DB 커밋에서 K4/B6 등이 누락되어 nextpnr가 실패한 기록이다. 이 기록은 보존하되 **‘DB가 없으니 종료’가 아니라 다음 원인 조사와 수정의 출발점**으로 사용한다.

| 순서 | 수행할 일 | 다음 단계로 넘어갈 근거 |
|---|---|---|
| 1 | 선택된 실행 파일·래퍼·릴리스·부품·패키지·DB 경로·커밋을 다시 대조한다 | 실수로 다른 버전이나 S50 자료를 사용하지 않았다는 실행 근거 |
| 2 | FPGAwars 패키지와 openXC7 상류의 릴리스·소스·DB 변경·공개 이슈와 수정본을 조사한다 | 비교할 후보와 변경 이유, 후보별 재현 명령 |
| 3 | S75의 패키지 핀 CSV·tilegrid·tileconn·IOB·프레임 자료와 bbaexport가 읽는 실제 경로를 검사한다 | 원본 DB 부족, 패키징 오류, 변환기 오류를 나눠 원인 특정 |
| 4 | 검증 가능한 DB·부품 매핑·변환기 수정 또는 맞는 릴리스로 chipdb를 다시 만든다 | 정확한 `xc7s75fgga484-1`과 필요한 핀의 매핑, DB·생성물 해시 |
| 5 | 작은 논리 게이트로 Yosys→nextpnr→FASM→frames→bit 전체를 실행한다 | 새 입력에서 새 bit 생성, 단계별 종료·보고서·해시 |
| 6 | 10개 모드·버튼·LCD를 포함한 학생 통합 RTL로 확장한다 | 사전 시뮬레이션, 자원·타이밍·제약 검사, 통합 bit 생성 |
| 7 | 캐시가 없는 새 clone과 고정된 도구·DB로 다시 실행한다 | 동일 소스에서 재현 가능한 명령·산출물·환경 기록 |

- 핀 이름 몇 개를 CSV에 넣어 오류 메시지만 없애지 않는다. 패키지 핀에서 실제 IOB·타일·라우팅·프레임까지 연결이 맞는지 검증한다.
- S50·다른 보드·다른 part로 대체하거나 필수 핀 제약·오류 검사를 끄는 방식은 이 S75 실습의 완료로 세지 않는다.
- 원래 선택한 패키지에서 멈추지 말고 공개 수정본·다른 정상 배포·필요한 소스 빌드와 도구 수정까지 조사한다. 수정한 버전은 커밋·패치·빌드 명령으로 재현할 수 있게 남긴다.
- 학생 환경에 Vivado를 요구하는 DB 생성 절차를 필수 준비 단계로 옮겨 놓지 않는다. 필요한 사전 생성 DB의 배포·라이선스·정확한 부품 지원을 확인하고 학생의 실제 빌드 과정은 오픈소스로 완결한다.
- 합성까지만 성공하거나 bit 파일이 존재한다는 이유로 완료 처리하지 않는다. 배치배선·프레임 변환·대상 part·입력 해시·생성 실행을 확인한다. 실제 보드 동작은 별도로 검증한다.
- 제작자에게 Mac이 없으므로 실제 빌드는 사용할 수 있는 Linux/WSL에서 수행한다. macOS ARM64용 도구 배포와 설치 경로를 확인하되 Mac 실행 결과라고 표시하지 않는다.
- board 미연결과 bit 생성 문제를 구분한다. 보드가 없어도 합성·배치배선·bit 생성·재현 검증 작업은 계속 진행한다.

조사 시작점은 [FPGAwars openXC7 패키지](https://github.com/FPGAwars/tools-openxc7), [openXC7 nextpnr](https://github.com/openXC7/nextpnr-xilinx), [openXC7 X-Ray DB](https://github.com/openXC7/prjxray-db), [기존 실패 분석](../example/fpga_projects_hdl/LAB1/docs/cli.md)이다. 이 계획서 작성은 S75 bit를 새로 생성했다는 보고가 아니다. 실행 단계에서 위 항목을 마쳐 성공 근거를 확보해야 한다.

### 6.3 openFPGALoader를 정식 필수 단계로 추가한다

openFPGALoader는 **이미 생성된 bitstream을 장치에 기록하는 도구**로 설명한다. RTL에서 bit를 만드는 앞 단계와 역할을 나누고, CLI 실습에는 두 단계 모두 포함한다. 공식 [시작 안내](https://trabucayre.github.io/openFPGALoader/guide/first-steps.html)와 [옵션·지원 목록](https://github.com/trabucayre/openFPGALoader)을 기준으로 명령을 확정한다.

1. Linux/WSL과 macOS ARM64의 설치 방법·실행 파일·버전을 확인한다. 필요하면 Windows 네이티브 지원 경로도 구분한다.
2. `openFPGALoader --help`, `openFPGALoader -V`, `openFPGALoader --list-cables`, `openFPGALoader --list-boards`, `openFPGALoader --list-fpga`로 도구와 지원 항목을 확인한다.
3. 실제 보드·케이블 종류, USB 장치, Linux 접근 권한을 확인한다. VM/WSL에서는 호스트에 연결된 USB가 게스트에 전달되는 단계와 결과까지 설명한다.
4. `openFPGALoader --scan-usb`와 케이블을 지정한 `--detect`로 탐색하고 JTAG IDCODE·인식된 FPGA를 기록한다. 부품의 패키지·속도 등급은 IDCODE 하나만으로 모두 확인했다고 주장하지 않고 보드 자료·빌드 설정과 대조한다.
5. 이번 CLI 실행에서 생성한 `build/cli/lab1_integrated.bit`의 경로·해시를 확인하고 SRAM 기록을 수행한다.
6. 실제 기록 로그와 장치 상태를 확인한다. 기록 성공과 회로 동작 성공을 구분하고 스위치·LED·10모드·버튼·LCD를 실측한다.
7. 전원 재인가 후 유지가 필요한 경우에만 별도 Flash 단계로 다룬다. `-f`의 의미와 대상 Flash·지원 설정을 확인한다. SRAM 실습과 섞어 설명하지 않는다.

교안에서 구체적인 케이블명이 확인되기 전의 명령 형태는 다음과 같다. `<실제_케이블명>`은 그대로 실행할 문자열이 아니라 지원 목록과 연결된 장비에서 확정할 값이다. 최종 학생 PDF에는 확인한 실제 값으로 채운다.

```sh
openFPGALoader -c <실제_케이블명> --detect
openFPGALoader -c <실제_케이블명> build/cli/lab1_integrated.bit
```

보드 프리셋이 실제 보드와 일치하면 `-b` 경로를 설명할 수 있다. 무관한 Arty 등의 예시 보드명을 수업 보드의 실제 명령처럼 복사하지 않는다. Flash용 `--verify`를 SRAM 기록의 검증 옵션이라고 안내하지 않는다.

- ‘Vivado 미설치·PATH 미등록’ 조건의 새 실행 환경에서 CLI 전 과정을 검증한다. 기존 Vivado bit·완성 예시·빌드 캐시를 참조하지 않는지 확인한다.
